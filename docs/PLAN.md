# RMC ERP — Build Plan

One phase per session/branch/PR, in order. A phase is not "done" until its
Definition of Done is fully met and `pnpm typecheck && pnpm lint && pnpm test`
are green with no regression against the prior phase's baseline.

Status legend: `not started` / `in progress` / `blocked` / `done`

**Mobile parity is continuous, not deferred.** Every phase that ships a
web screen ships the equivalent mobile screen(s) in the same phase, against
the same generated hooks — mobile is not a catch-all built after the fact.
A phase is not "done" if a module works on web but not on mobile for the
roles that need it (see §6 Roles in `DOMAIN.md` / the original spec for
who works from the field vs. a desk). Phase 10 below is scoped down
accordingly: by the time it starts, every module already has its mobile
screens from its own phase, so Phase 10 is only the mobile-specific
concerns a per-module phase wouldn't otherwise cover — offline queueing,
sync conflict handling, and push notification deep links.

| 3 | Production | done | Mix designs + ingredients (per branch/product recipe, `packages/db`'s `mixDesign`/`mixDesignIngredient`). Production orders as an explicit allowed-transition state machine (`packages/core`'s `productionStateMachine.ts`: `planned→in_progress→completed`, +`cancelled` from either; completion blocked below one batch). Recording a batch is the inventory-deduction event: back-flushes every ingredient (recipe rate × actual m³, uniformly moisture-adjusted — see below) against a `StockBalance` row at moving-average cost (`packages/core`'s `applyStockReceipt`/`applyStockConsumption`, recomputed transactionally on every receipt/consumption per DOMAIN.md Invariant 8), auto-transitioning the order to `in_progress` on its first batch. `StockAdjustment` is how stock enters the system as a manual receipt (re-averaging cost) or correction/write-off, since Phase 9's Goods Receipt doesn't exist yet — a documented interim, like Phase 2's credit-check exposure proxy. A consumption that would take an ingredient negative is blocked (409) unless a mandatory-reason override (`productionOrders:approve` permission, audited) is supplied, mirroring Phase 2's credit-block pattern. Returned concrete recorded per production order (does not reverse stock — materials were already consumed at batching); yield variance (batched vs returned m³) computed on demand, with a `deliveryVarianceM3` field left `null` until Phase 5's DeliveryOrder exists to supply actual delivered m³ (documented, not guessed). **Moisture correction is a documented placeholder** (`packages/core`'s `applyUniformMoistureAdjustment`): applies one uniform basis-points factor to every ingredient rather than the industry-standard practice of correcting only aggregates with an offsetting trim to added water — flagged in code the same way CLAUDE.md flags unverified JoFotara fields, not presented as authoritative. Web screens for planning/back-office (mix designs, stock, production-order CRUD, batch/return recording, yield variance). Mobile ships the batch-recording screen for plant Operators — list + detail with the batch form (incl. the negative-stock override flow) and returned-concrete recording; production-order *creation* and cancellation stay web-only (a planning/back-office decision, called out rather than silently dropped), matching DOMAIN's "web for planning, mobile for the plant floor" split. Integration tests (real Postgres): moving-average cost math across receipts, back-flush consumption math (incl. moisture adjustment), negative-stock block + override, sequential batch numbering, completion gate, and yield variance. |
| 4 | QC | done | Fresh tests (`QCFreshTest`: slump, temperatures, air content — data capture only, no pass/fail) and cube tests (`QCCubeTestSet` + `QCCubeTestSpecimen`) linked to a batch. Pass/fail (`packages/core`'s `evaluateCubeTest`) is rendered only when a set's `ageDays` equals its `designAgeDays` (28 by default) — a product's characteristic strength is by definition a design-age figure, so earlier ages (7-day etc.) are recorded with `pass: null` rather than guessing a maturity-conversion formula. A failing design-age result flags the **batch** (`batch_record.qcFlagged`/`qcFlagReason`, added by migration) and writes a `Notification` row — DOMAIN.md's "flags every delivery drawn from that batch" is interim-scoped to the batch level (documented, like Phase 3's `deliveryVarianceM3` null field) since Phase 5's DeliveryOrder doesn't exist yet; Phase 5 will propagate the flag onto deliveries drawn from a flagged batch. `Notification` is introduced here as a company/branch-scoped broadcast log (visible to anyone in the company, not per-user targeted) since DOMAIN.md's cross-cutting `Notification` entity had no consumer before this phase — Phase 10 owns the real per-user inbox + typed deep-link resolver. Batch traceability report (cube result → batch → mix design, `GET /qc/cube-test-sets` + detail) with pass/fail/pending filtering; delivery-order traceability is explicitly deferred to Phase 5, not guessed. Web: QC recording embedded in the Production Orders batch table (fresh/cube test forms per batch, qcFlagged badge) plus a dedicated QC page (notifications inbox + traceability report with filters). Mobile: QC recording embedded in the production-order detail screen (matching web's per-batch placement) plus a "QC Alerts" screen (unread-notification inbox) for QC Technicians to see failures on-site — traceability reporting stays web-only (a QA/back-office analysis tool, not a field task, matching the "field roles" mobile-parity rule). Integration tests (real Postgres): pass/fail at design age (boundary-exact pass), no-verdict before design age, failing result flags the batch and raises a notification (read via `/notifications`, marked read), 400 when a product has no characteristic strength configured, and traceability listing/filtering/detail. |
| 5 | Dispatch | done | `DeliveryOrder` (`packages/core`'s `deliveryStateMachine.ts`: `planned→dispatched→delivered→invoiced`; DOMAIN.md documents no cancellation state for it, unlike SalesOrder/ProductionOrder, so a bad delivery order is voided rather than transitioned — not guessed in). `Truck`/`Driver` master data (branch-scoped); `Driver` carries an optional `userId` link to an `app_user` login so the mobile app can resolve "my assigned deliveries" — a small, non-domain-sensitive schema addition (an internal FK, not a guessed business format), introduced here since Phase 5 is the first phase needing that identity. Credit check re-evaluated at dispatch (reusing Phase 2's `evaluateCreditCheck` against the customer's current total confirmed/fulfilled exposure, this time with `newOrderAmountFils: 0` since the order's own total is already included) — a `block`-policy customer over their limit returns 409 unless a mandatory-reason override is supplied, requiring `deliveryOrders:approve` and audited, mirroring Phase 2/3's override pattern. DOMAIN.md Invariant 5 (cannot be `delivered` without proof of delivery carrying a customer signature) is enforced **structurally**: `POST /delivery-orders/:id/deliver` is the only delivered-transition route, and it creates the `ProofOfDelivery` row in the same transaction — there is no way to reach `delivered` without one. QC-flag propagation from Phase 4 finally lands: a delivery order's `qcFlagged`/`qcFlagReason` are derived (not duplicated) from the batch it references via `batchRecordId`, closing that phase's forward reference. Phase 3's `deliveryVarianceM3` forward reference also closes: `GET /production-orders/:id/yield-variance` now sums delivered/invoiced deliveries' actual received m³ instead of returning `null` unconditionally. Web: Trucks/Drivers master-data screens; a Dispatch Board (branch/date-scoped Gantt-style planned-vs-actual timeline built from scheduled/dispatched/delivered timestamps, plus delivery-order creation and dispatch with credit-block/override handling) for Dispatchers. Mobile: a dependency-free `SignaturePad` (PanResponder-captured strokes serialized to a real `data:image/svg+xml` image on submit, matching `PickerField`'s no-library precedent) powers a driver's "My Deliveries" screen (assigned + dispatched, proof-of-delivery capture with signature) and a simplified mobile dispatcher view (actionable list + per-delivery dispatch action); the Gantt visualization itself stays web-only, a planning tool rather than a field action, matching Phase 3's "web for planning, mobile for execution" split. Integration tests (real Postgres): creation against a confirmed sales order, full dispatch→deliver lifecycle with proof of delivery, delivery cannot skip dispatch, credit-block at dispatch + override, QC-flag propagation from a failed batch onto its delivery (list and detail), dispatch-schedule listing, and yield-variance closing with a real delivered quantity. |
| 6 | Invoicing | done | Invoice engine (`POST /delivery-orders/:id/invoice`): combined invoice (one invoice, two lines: taxable concrete + exempt transport) or split pair (two invoices, one line each, cross-referencing each other via `relatedInvoiceId`) generated atomically from a `delivered` delivery order, reusing Phase 2's `computeLineBaseAmounts` for per-line tax math (rounded half-up, then summed to header subtotal/tax/total). Requires the delivery order to carry a `salesOrderLineId` (new nullable FK added to `deliveryOrder` in this phase, set at delivery-order creation) so invoicing knows exactly which order line's price/tax rate to bill, since a sales order can have multiple lines. Double-billing prevented by a **unique constraint** — `UNIQUE(deliveryOrderId, taxTreatment)` on `invoice_line`, not application logic alone — sized to allow split mode's two rows (taxable + exempt) against the same delivery order while still blocking a genuine re-bill. `packages/core`'s `invoiceStateMachine.ts` defines the full lifecycle (`draft→pending_clearance→cleared→issued→partially_paid→paid`, +`rejected`↔`draft`) but this phase only ever creates `draft` invoices; clearance/payment transitions are Phase 7/8's job, documented rather than guessed at here. Credit/debit notes reference their invoice and get their own gapless numbers (`CN-`/`DN-` prefix) via the same counter mechanism, generalized with a `docType` discriminator column (`UNIQUE(branchId, docType, yearMonth)`) so invoice and note numbering share one atomic upsert-increment helper without colliding. Gapless per-branch-per-year numbering `{BRANCH}-{YYMM}-{SEQ}` allocated inside the same transaction as the document via `INSERT ... ON CONFLICT DO UPDATE SET next_seq = next_seq + 1 RETURNING`. Concurrency correctness for "exactly once" invoicing uses `SELECT ... FOR UPDATE` on the delivery-order row as the serialization primitive (a thrown constraint violation would abort the whole Postgres transaction uncatchably, so `.onConflictDoNothing()` is used as the non-throwing backstop instead) — proven with a real `Promise.all` of two simultaneous HTTP invoice-generation requests in the integration suite, asserting exactly one succeeds. Introduces `Idempotency-Key` middleware (`apps/api/src/middleware/idempotency.ts`, CLAUDE.md Hard Rule) and applies it to this phase's three POST routes (generate invoice, credit note, debit note): replays the stored response for a repeated key, 409s a same-key request still in flight, 422s a same-key reuse with a different request body. **Retrofitting `Idempotency-Key` onto Phases 1–5's existing POST routes is scoped out as documented follow-up, not silently skipped** — it was a pre-existing gap discovered, not introduced, in this phase. Similarly, a pre-existing `Promise.all([tx.select(), tx.select()])`-on-one-shared-transaction anti-pattern (unsupported by `pg`, surfaced via a live deprecation warning) was found repeated across ~20 route files from Phases 1–6 for list-endpoint pagination; fixed in this phase's own new code (`loadInvoiceDetail`, serialized to sequential awaits) with the wider retrofit likewise documented as follow-up rather than attempted mid-phase. Web: Accountant-facing Invoices screen — generate (delivery-order picker filtered to `delivered`, combined/split mode), status-filterable paginated list, detail panel (lines, subtotal/tax/total, credit/debit note lists + add forms). Mobile: read-only invoice list (status filter) and detail screens for Sales Reps and Collectors — no create/edit, matching the phase's Accountant-vs-field-role split. Integration tests (real Postgres): combined-mode tax math + delivery-order transition to `invoiced`, 400 when not yet delivered, 400 when no `salesOrderLineId`, split-mode cross-referencing, double-billing 400 on a second attempt, the two-simultaneous-requests concurrency test, gapless sequential numbering across invoices, credit/debit note creation, and Idempotency-Key replay + conflict-on-reuse. |

## Working rules recap

- Loop per phase: migration → OpenAPI contract → server route + service →
  tests → generated client hooks → UI → `pnpm typecheck && pnpm lint && pnpm
  test` green → conventional commit → update this file's status column.
- Reports and exports (CSV/XLSX, server-side filtered + paginated) are built
  inside the phase that owns the underlying data — never deferred to a
  separate "reports phase."
- If a phase is too large once underway, split it and say so rather than
  shipping a stub.

## Decisions locked before Phase 0 (2026-09-06)

- New repo `sanaddmour-byte/rmixerp`, separate from the unrelated `crisp`
  marketing site.
- Deployment: generic Docker/Compose, no provider-specific config until a
  provider is chosen.
- Auth: custom JWT + refresh tokens (no third-party auth provider).
- Tenancy: single-tenant at go-live; `company_id` present everywhere per
  Hard Rules so multi-company is a future data change, not a rewrite.
- JoFotara/ISTD: no credentials yet. Build `MockClearanceProvider` as the
  active default and the `JoFotaraProvider` shell against the interface,
  with unverified field mappings flagged rather than guessed.
