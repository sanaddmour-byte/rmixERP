# RMC ERP — Build Plan

One phase per session/branch/PR, in order. A phase is not "done" until its
Definition of Done is fully met and `pnpm typecheck && pnpm lint && pnpm test`
are green with no regression against the prior phase's baseline.

Status legend: `not started` / `in progress` / `blocked` / `done`

**Mobile parity is continuous, not deferred.** Every phase that ships a
web screen ships the equivalent mobile screen(s) in the same phase, against
the same generated hooks — mobile is not a catch-all built after the fact.
A phase is not "done" if a module works on web but not on mobile for the
roles that need it (see §6 Roles in `DOMAIN.md` / the original spec for
who works from the field vs. a desk). Phase 10 below is scoped down
accordingly: by the time it starts, every module already has its mobile
screens from its own phase, so Phase 10 is only the mobile-specific
concerns a per-module phase wouldn't otherwise cover — offline queueing,
sync conflict handling, and push notification deep links.

Recording a batch is the inventory-deduction event: back-flushes every ingredient (recipe rate × actual m³, uniformly moisture-adjusted — see below) against a `StockBalance` row at moving-average cost (`packages/core`'s `applyStockReceipt`/`applyStockConsumption`, recomputed transactionally on every receipt/consumption per DOMAIN.md Invariant 8), auto-transitioning the order to `in_progress` on its first batch. `StockAdjustment` is how stock enters the system as a manual receipt (re-averaging cost) or correction/write-off, since Phase 9's Goods Receipt doesn't exist yet — a documented interim, like Phase 2's credit-check exposure proxy. | 6 | Invoicing | done | Invoice engine (`POST /delivery-orders/:id/invoice`): combined invoice (one invoice, two lines: taxable concrete + exempt transport) or split pair (two invoices, one line each, cross-referencing each other via `relatedInvoiceId`) generated atomically from a `delivered` delivery order, reusing Phase 2's `computeLineBaseAmounts` for per-line tax math (rounded half-up, then summed to header subtotal/tax/total). Requires the delivery order to carry a `salesOrderLineId` (new nullable FK added to `deliveryOrder` in this phase, set at delivery-order creation) so invoicing knows exactly which order line's price/tax rate to bill, since a sales order can have multiple lines. Double-billing prevented by a **unique constraint** — `UNIQUE(deliveryOrderId, taxTreatment)` on `invoice_line`, not application logic alone — sized to allow split mode's two rows (taxable + exempt) against the same delivery order while still blocking a genuine re-bill. `packages/core`'s `invoiceStateMachine.ts` defines the full lifecycle (`draft→pending_clearance→cleared→issued→partially_paid→paid`, +`rejected`↔`draft`) but this phase only ever creates `draft` invoices; clearance/payment transitions are Phase 7/8's job, documented rather than guessed at here. Credit/debit notes reference their invoice and get their own gapless numbers (`CN-`/`DN-` prefix) via the same counter mechanism, generalized with a `docType` discriminator column (`UNIQUE(branchId, docType, yearMonth)`) so invoice and note numbering share one atomic upsert-increment helper without colliding. Gapless per-branch-per-year numbering `{BRANCH}-{YYMM}-{SEQ}` allocated inside the same transaction as the document via `INSERT ... ON CONFLICT DO UPDATE SET next_seq = next_seq + 1 RETURNING`. Concurrency correctness for "exactly once" invoicing uses `SELECT ... FOR UPDATE` on the delivery-order row as the serialization primitive (a thrown constraint violation would abort the whole Postgres transaction uncatchably, so `.onConflictDoNothing()` is used as the non-throwing backstop instead) — proven with a real `Promise.all` of two simultaneous HTTP invoice-generation requests in the integration suite, asserting exactly one succeeds. Introduces `Idempotency-Key` middleware (`apps/api/src/middleware/idempotency.ts`, CLAUDE.md Hard Rule) and applies it to this phase's three POST routes (generate invoice, credit note, debit note): replays the stored response for a repeated key, 409s a same-key request still in flight, 422s a same-key reuse with a different request body. **Retrofitting `Idempotency-Key` onto Phases 1–5's existing POST routes is scoped out as documented follow-up, not silently skipped** — it was a pre-existing gap discovered, not introduced, in this phase. Similarly, a pre-existing `Promise.all([tx.select(), tx.select()])`-on-one-shared-transaction anti-pattern (unsupported by `pg`, surfaced via a live deprecation warning) was found repeated across ~20 route files from Phases 1–6 for list-endpoint pagination; fixed in this phase's own new code (`loadInvoiceDetail`, serialized to sequential awaits) with the wider retrofit likewise documented as follow-up rather than attempted mid-phase. Web: Accountant-facing Invoices screen — generate (delivery-order picker filtered to `delivered`, combined/split mode), status-filterable paginated list, detail panel (lines, subtotal/tax/total, credit/debit note lists + add forms). Mobile: read-only invoice list (status filter) and detail screens for Sales Reps and Collectors — no create/edit, matching the phase's Accountant-vs-field-role split. Integration tests (real Postgres): combined-mode tax math + delivery-order transition to `invoiced`, 400 when not yet delivered, 400 when no `salesOrderLineId`, split-mode cross-referencing, double-billing 400 on a second attempt, the two-simultaneous-requests concurrency test, gapless sequential numbering across invoices, credit/debit note creation, and Idempotency-Key replay + conflict-on-reuse. |
| 7 | Clearance | done | `ClearanceProvider` interface in `packages/core` (`clearanceProvider.ts`: `submit(input): Promise<ClearanceOutcome>`, outcome is `cleared \| rejected \| transport_error` — a real discriminated union, not a boolean, so business rejection and transport failure are handled differently by construction) with `MockClearanceProvider` as the default, always-clears implementation; `apps/api/src/clearance/jofotara/provider.ts` is a real shell (client-id/secret headers, Base64-encoded UBL XML in a JSON POST body, matching the general shape of JoFotara's public documentation) but is **not** wired up as the active provider anywhere — `providerFactory.ts` only selects it when `CLEARANCE_PROVIDER=jofotara` is explicitly configured. Every field whose exact name/placement isn't confirmed against ISTD's own technical spec (intake endpoint, auth flow, request/response field names, the ICV's real XML placement, credit/debit note document shape, QR payload format) is tagged `// VERIFY:` in `provider.ts`/`ubl.ts`/`mapping.ts` and enumerated with sources in the new `docs/JOFOTARA-OPEN-QUESTIONS.md` — nothing there is presented as authoritative. `apps/api/src/clearance/ubl.ts` builds a real, generic UBL 2.1 XML document (OASIS-standard element set and UN/CEFACT type codes 388/381/383) with the invoice's own id reused as the UBL UUID. `invoiceStateMachine.ts`'s `draft→pending_clearance→cleared/rejected→issued` transitions are wired up for the first time here (Phase 6 only ever created `draft`); a `rejected` invoice's `draft` reopen edge exists in the table but this phase does not build a correction/resubmission flow for it (documented follow-up, not guessed). Clearance-before-issue is enforced explicitly at the service layer (`POST /invoices/:id/issue` 400s with a named reason if the invoice isn't `cleared`, on top of the state machine already only allowing that edge) — the same structural pattern as Phase 5's proof-of-delivery gate. "A cleared invoice can only be credit-noted, never edited" is enforced the same way: `POST /invoices/:id/credit-notes` and `.../debit-notes` (Phase 6) now 400 unless the invoice is `cleared` or later, closing a gap Phase 6 couldn't close before real clearance existed. A `clearanceStatus` column (`pending/cleared/rejected/retrying`) plus `clearanceIcv`/`clearanceQrPayload`/`clearanceProviderReference`/`clearanceAttempts`/`clearanceNextRetryAt`/`clearanceError`/submitted+response jsonb payloads is added to `invoice`, `credit_note`, and `debit_note` alike (a finer-grained, per-submission status than `invoiceStatus` — necessary since credit/debit notes have no state machine of their own to piggyback on). ICV allocation (`clearance_icv_counter`, one gapless counter per company, matching CLAUDE.md's single-tenant/single-registered-income-source model) happens once per *document*, not per attempt — a retry reuses the same ICV rather than burning a new one, matching how a real e-invoicing counter must correspond to actual documents. Submission is two-phase by design: a short transaction reserves the attempt (row lock + `.for("update")`, same idempotency mechanism as Phase 6's invoice generation) so a concurrent duplicate submission is rejected before ever reaching the provider; the provider call itself runs with no transaction open (a real HTTP round-trip inside a held row lock would be a lock-contention hazard Phase 6's pure-DB work never had to consider); a second short transaction persists the outcome. Bounded exponential-backoff retry (`packages/core`'s `computeRetryDelayMs`: 30s base, doubling, capped at 30min, giving up after `MAX_CLEARANCE_ATTEMPTS`) runs via a `node-cron` job (every minute) that only ever picks up `retrying` rows past their `clearanceNextRetryAt` — a business `rejected` outcome is terminal and never auto-retried; a row that exhausts its attempts simply stops being picked up automatically and waits for a human to retry it from the queue screen. Web: a "Submit for Clearance"/"Retry"/"Issue" action set added to the existing Accountant-facing Invoices screen (clearance status, ICV, QR payload, and any error surfaced inline), plus a new back-office-only Clearance Queue screen listing all three document types with status/type filters and a manual retry action — no mobile equivalent, per CLAUDE.md's explicit back-office-screen exception (same reasoning as Phase 9's GL/financial-statement screens). Integration tests (real Postgres, `apps/api/test/clearance.test.ts`): clearing a draft invoice via the mock provider (ICV/QR persisted), 400 re-submitting an already-cleared invoice, 404 on an unknown id, strictly-increasing ICVs across distinct documents, clearance-before-issue enforcement (both directions), credit-note clearance submitted independently of its parent invoice, clearance-queue filtering by status/documentType, and a dedicated transport-failure retry test (using a custom always-failing `ClearanceProvider`, called directly against the service layer) proving `clearanceStatus` becomes `retrying` with a scheduled `clearanceNextRetryAt` and an incrementing attempt count while `invoiceStatus` itself never moves — and that the same ICV is reused across retries and survives into the eventual successful clearance. |

## Working rules recap

- Loop per phase: migration → OpenAPI contract → server route + service →
  tests → generated client hooks → UI → `pnpm typecheck && pnpm lint && pnpm
  test` green → conventional commit → update this file's status column.
- Reports and exports (CSV/XLSX, server-side filtered + paginated) are built
  inside the phase that owns the underlying data — never deferred to a
  separate "reports phase."
- If a phase is too large once underway, split it and say so rather than
  shipping a stub.
